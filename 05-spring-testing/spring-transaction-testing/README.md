# Transaction Testing

This example demonstrates **transaction testing** in Spring.

It focuses on how Spring manages transactions during tests, how database changes are visible within a test transaction, and how Spring rolls back those changes after the test completes.

## What This Example Demonstrates

- Spring-managed test transactions.
- The `@Transactional` annotation in tests.
- Automatic rollback of test transactions.
- Verifying database changes within a transaction.
- Using `@AfterTransaction` to verify database state after a transaction ends.
- Testing database interactions with `JdbcTemplate` and H2.
- The difference between test transaction behavior and committed application transactions.

---

## What Is Transaction Testing?

Transaction testing verifies how database operations behave within transactional boundaries.

A transaction groups database operations into a unit of work. Depending on how the transaction completes, its changes may be committed or rolled back.

A simplified transaction flow looks like:

```text
Test Starts
    |
    v
Transaction Begins
    |
    v
Database Operation
    |
    v
Assertions Within Transaction
    |
    v
Test Completes
    |
    v
Transaction Rolls Back
    |
    v
Database Returns to Previous State
```

Spring's testing support can manage transactions automatically, making it easier to test database behavior without leaving persistent changes behind.

---

## Test-Managed Transactions

Spring TestContext supports test-managed transactions through Spring's transaction testing infrastructure.

A test method can use `@Transactional`:

```java
@Test
@Transactional
void shouldRollBackDatabaseChangesAfterTest() {
    // Perform database operations and assertions.
}
```

When the test framework supports transaction management and a suitable transaction manager is available, Spring starts a transaction before the test method executes.

By default, the transaction is rolled back after the test.

This helps keep tests isolated and prevents one test's database changes from affecting another.

---

## The Database Used in This Example

This example uses an embedded H2 database and `JdbcTemplate`.

The database schema defines a table for records created during testing:

```sql
CREATE TABLE transaction_records (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    message VARCHAR(255) NOT NULL
);
```

Spring Boot initializes the schema when the application context starts.

`JdbcTemplate` provides a convenient way to execute SQL statements without requiring additional entity or repository classes.

This keeps the example focused on transaction behavior.

---

## Writing Data Within a Test Transaction

The test inserts a record:

```java
jdbcTemplate.update("INSERT INTO transaction_records (message) VALUES (?)", "Created during test");
```

It then queries the table:

```java
Long count = jdbcTemplate.queryForObject("SELECT COUNT(*) FROM transaction_records", Long.class);

assertEquals(1L, count);
```

The record is visible within the current transaction, so the count is one.

This demonstrates that rollback does not prevent database operations from occurring. Instead, it determines whether those changes remain after the transaction ends.

---

## Automatic Rollback

Spring test-managed transactions are rolled back by default.

Conceptually:

```text
Before Test
    |
    v
Empty Table
    |
    v
Test Transaction Begins
    |
    v
Record Inserted
    |
    v
Count = 1
    |
    v
Test Completes
    |
    v
Transaction Rolled Back
    |
    v
Empty Table
```

The database changes made inside the transaction are discarded when the transaction rolls back.

This behavior is useful for tests that need to create temporary data without permanently modifying the database.

---

## Verifying the State After the Transaction

The example uses `@AfterTransaction`:

```java
@AfterTransaction
void shouldVerifyDatabaseChangesWereRolledBack() {
    Long count = jdbcTemplate.queryForObject("SELECT COUNT(*) FROM transaction_records", Long.class);

    assertEquals(0L, count);
}
```

The `@AfterTransaction` annotation identifies a method that Spring's test framework invokes after the test-managed transaction has ended.

Because the transaction has already been rolled back, the query verifies the database state outside the test transaction.

The record inserted by the test should no longer exist.

This is important because checking the database only inside the test transaction would not prove that rollback occurred.

---

## Why `@AfterTransaction`?

Consider the difference between these assertions:

### Inside the Transaction

```java
assertEquals(1L, count);
```

This verifies that the inserted record is visible within the transaction.

### After the Transaction

```java
@AfterTransaction
void shouldVerifyDatabaseChangesWereRolledBack() {
    assertEquals(0L, queryRecordCount());
}
```

This verifies that the record is absent after the transaction ends.

Together, the assertions demonstrate the complete transaction lifecycle.

## Test Transactions vs Application Transactions

Test-managed transactions and application-managed transactional operations serve related but different purposes.

### Test-Managed Transaction

```text
Test Framework
      |
      v
Transaction Begins
      |
      v
Test Executes Database Operations
      |
      v
Transaction Rolls Back by Default
```

The test framework controls the transaction boundary.

### Application Transaction

```text
Application Method
       |
       v
Transaction Begins
       |
       v
Business Operations
       |
       v
Transaction Commits or Rolls Back
```

Application transactions normally follow the application's transaction configuration and completion rules.

A test's automatic rollback should not be mistaken for the behavior of every transaction executed by the application.

## Rollback and Commit Behavior

Spring provides test annotations for controlling the outcome of test-managed transactions.

### Default Rollback

A transactional test is rolled back by default:

```java
@Test
@Transactional
void shouldRollBackDatabaseChangesAfterTest() {
    // Database changes are rolled back after the test.
}
```

### Explicit Rollback

The rollback behavior can be made explicit with `@Rollback`:

```java
@Test
@Transactional
@Rollback
void shouldRollBackChanges() {
    // Database changes are rolled back after the test.
}
```

### Commit

A test can request a commit with `@Commit`:

```java
@Test
@Transactional
@Commit
void shouldCommitChanges() {
    // Database changes are committed when the test transaction completes.
}
```

Committed test data can affect later tests. Tests using `@Commit` should therefore manage their database state deliberately.

This example uses the default rollback behavior and does not commit test data.

---

## Important Testing Considerations

### Rollback Does Not Mean No Database Changes Occurred

SQL statements still execute within the transaction. The rollback determines whether transactional changes persist after the transaction completes.

### A Suitable Transaction Manager Is Required

Spring must have an appropriate transaction manager and transactional resources configured for test-managed transactions to work.

### External Effects May Not Be Rolled Back

Database rollback does not automatically undo effects outside the transaction, such as messages already sent to an external system or HTTP requests already made to another service.

### Transaction Boundaries Matter

Assertions made inside a transaction may observe uncommitted changes that would not be visible to another transaction.

Tests should account for transaction boundaries when verifying persistence and isolation behavior.

## Key Takeaways

- Spring supports test-managed transactions through its TestContext framework.
- `@Transactional` can run a test method within a transaction.
- Test-managed transactions roll back by default.
- Database changes can be visible within a test transaction but absent afterward.
- `@AfterTransaction` allows verification after the test transaction has ended.
- H2 provides an embedded database suitable for this focused example.
- `JdbcTemplate` makes database operations straightforward without requiring JPA.
- `@Commit` and `@Rollback` can control test transaction outcomes.
- Database rollback does not undo every possible external side effect.
- Test-managed transactions and application transaction behavior should be understood separately.
